# رفع مشکل دکمه پرداخت زرین‌پال

## یافته‌های قابل اثبات از کد

- صفحه `checkout/[id]/page.tsx` فرم پرداخت را واقعاً رندر می‌کند. دکمه قبلی `type="button"` و `onClick` داشت؛ شروع پرداخت فقط پس از اجرای JavaScript ممکن بود. خطا نیز فقط با Toast گزارش می‌شد.
- کامپوننت قبلی روی تمام روش‌های پرداخت `loadStripe` را در سطح ماژول اجرا می‌کرد، حتی بدون کلید Stripe. اکنون از ورودی `pure` استفاده می‌شود و فقط هنگام رندر روش Stripe فراخوانی می‌شود. این نقص قطعی در کد است، اما علت قطعی مشکل Production بدون لاگ مرورگر اثبات نشده است.
- ارسال جدید یک فرم ساخته‌شده در Server Component با Server Action است. فرم به صورت slot وارد خلاصه سفارش می‌شود و در نمایش موبایل و دسکتاپ وجود دارد. ارسال استاندارد فرم پیش از Hydration هم پشتیبانی می‌شود؛ پس از Hydration، `useFormStatus` دکمه را غیرفعال و متن انتظار را نمایش می‌دهد. شروع خودکار قبلی حذف شده و پرداخت با ارسال فرم آغاز می‌شود.
- Server Action جدید همان پیاده‌سازی موجود را صدا می‌زند؛ Redirect بیرون از catch اجرا می‌شود. شکست شروع پرداخت به همان صفحه با پیام فارسی بازمی‌گردد؛ خطاهای رندر/ارسال نیز Error Boundary دارند.
- مبلغ از سفارش متعلق به کاربر در MongoDB خوانده می‌شود. Authority با فرمت معتبر ذخیره و سپس StartPay انتخاب می‌شود. درخواست‌های API حداکثر ۳۰ ثانیه منتظر می‌مانند.
- قفل اتمیک شروع پرداخت و استفاده مجدد از Authority موجود حفظ شده است. ثبت پرداخت در Callback فقط پس از Verify معتبر با کد 100/101 و ref_id معتبر و با شرط اتمیک `isPaid: false` انجام می‌شود. مسیر ثبت دستی و مسیرهای PayPal/Stripe اجازه ثبت سفارش زرین‌پال را ندارند.
- ثبت لاگ شامل مرحله، نوع خطا و کد پاسخ است؛ Merchant ID، Authority، اطلاعات کارت و خطای خام رسید در لاگ جدید نوشته نمی‌شوند.

## اعتبارسنجی محلی

```sh
node --test tests/zarinpal.test.cjs
npx tsc --noEmit
npm run build
git diff --check
```

تست‌ها API و دیتابیس را شبیه‌سازی می‌کنند. این‌ها تأیید پرداخت واقعی، اتصال شبکه Liara یا Hydration در مرورگر مشتری نیستند. هیچ سفارش واقعی در این بررسی پرداخت‌شده فرض نمی‌شود.

## Liara و تشخیص قطعی Production

متغیر محیطی جدیدی لازم نیست. تنظیمات موجود را حفظ کنید: Secret با نام `ZARINPAL_MERCHANT_ID` و `ZARINPAL_CALLBACK_BASE_URL=https://viora-store.ir`. مقدار دوم فقط origin است؛ مسیر Callback را برنامه اضافه می‌کند. همین Commit باید در Liara Build و Deploy شود. تغییر `.env.local` لازم نیست.

اگر مشکل ادامه داشت، این شواهد را با زمان دقیق و بدون Cookie، Authorization، Secret یا محتوای اطلاعات شخصی جمع‌آوری کنید:

1. شناسه Commit و Deploy فعال Liara و تأیید اینکه HTML و فایل‌های JavaScript از همان Deploy هستند.
2. اولین خطای Console و stack آن پس از بارگذاری مجدد صفحه و کلیک؛ به‌خصوص Hydration، ChunkLoadError، خطای Stripe یا Server Action.
3. نتیجه بارگذاری فایل‌های `/_next/static` و اینکه پس از ارسال فرم POST ایجاد می‌شود؛ فقط URL مسیر بدون مقادیر خصوصی، status و وجود هدر `Next-Action` کافی است.
4. لاگ Liara در همان زمان، شامل `[zarinpal]` و مرحله شکست یا پیام `Failed to find Server Action` و خطاهای Origin/Host. هیچ HAR حاوی Session منتشر نشود.
5. روش پرداخت سفارش باید دقیقاً `ZarinPal` باشد؛ وضعیت `isPaid` و وجود Authority را بدون انتشار مقادیر خصوصی گزارش کنید.

در صورت اثبات `Failed to find Server Action`، یکسان بودن Build بین replicaها و assets بررسی شود. تنظیم کلید مشترک `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` فقط در صورت نیاز چند instance و مطابق مستندات Next بررسی شود؛ برای این اصلاح به صورت پیش‌فرض کلید جدیدی لازم نیست.

مراجع رسمی: [فرم‌ها و Server Actions](https://nextjs.org/docs/app/guides/forms)، [خطای یافت‌نشدن Server Action](https://nextjs.org/docs/messages/failed-to-find-server-action).

بعد از Deploy، پرداخت کم‌مبلغ واقعی، لغو پرداخت و تکرار Callback را بررسی کنید. Authority ذخیره‌شده عمداً دوباره استفاده می‌شود؛ برای Authority منقضی یا درخواست با نتیجه نامعلوم، ابتدا وضعیت تراکنش در زرین‌پال بررسی شود. قفل محلی تضمین ثبت اتمیک سفارش است و جای تطبیق تراکنش با سرویس خارجی را نمی‌گیرد.
